# 목적지 허브 탭 설계 메모 — 제주 · 울릉도

> 1~8절 = 제주(먼저 착수). 9절 = 울릉도(제주 완료 후).

> 상태: **설계만 완료, 코드 미적용.** 토큰 여유 있을 때 진행.
> 목적: 전국 제주행 배편을 한 탭에서 보는 `/jeju` 페이지 추가.

---

## 1. 데이터 실측 (MTIS 7일치)

제주행(육지 → 제주) 출발항은 **5곳**이다.

| 출발항 | 7일 총편수 | 운항일 | 일평균 | 선박 | 현재 커버 |
|---|---|---|---|---|---|
| 목포 | 18편 | 6/7 | 2.6 | 퀸제누비아2·퀸제누비아·퀸메리 | ✅ |
| 완도 | 16편 | 4/7 | 2.3 | 한일골드스텔라·실버클라우드·송림블루오션 | ✅ |
| **진도** | 12편 | 6/7 | 1.7 | 산타모니카 | ❌ |
| **녹동**(고흥) | 6편 | 6/7 | 0.9 | 아리온제주 | ❌ |
| **삼천포**(사천) | 4편 | 4/7 | 0.6 | 오션비스타제주 | ❌ |

- 제주발(제주 → 육지)도 같은 5개 항구로 대칭이다.
- **부산·인천발 제주 항로는 MTIS에 없다.** (7일 조회 전체에서 0건)
- 완도가 4/7일뿐인 것은 격일 운항 선박이 섞여 있기 때문. 하루치만 보고 판단하면 안 된다.

**신규로 얻는 것: 진도·녹동·삼천포 = 일평균 3.2편.**

## 2. 핵심 판단 — 완도·목포에서 제주를 **빼지 말 것**

원안은 "완도·목포에서 제주를 제외하고 제주 탭으로 이관"이었으나, **빼지 않는 쪽을 강하게 권한다.**

1. **완도→제주는 완도의 최대 노선이다.** 하루 4편, 대형 카페리. 완도 방문자의 핵심 확인 대상이다.
2. **핵심 원칙 #1 "클릭 없이 바로" 위배.** 완도 주민·여행객이 제주 배를 보려고 탭을 옮겨야 한다면
   이 앱의 존재 이유를 스스로 깎는 것이다.
3. **중복은 문제가 아니다. 두 탭의 질문이 다르다.**
   - 완도 탭 = "완도에서 오늘 어디로 갈 수 있나"
   - 제주 탭 = "제주 가는 배가 어디서 뜨나 / 오늘 뜨나"
4. **검색 유입도 갈린다.** "완도 제주 배편" → 완도 탭 / "제주도 배편" → 제주 탭.
   제주는 검색량이 나머지 4개 지역을 합친 것보다 클 가능성이 높다. 제주 탭은 **SEO 관점의 최대 기회**다.

> 결론: 제주 탭은 **추가**하되 기존 노선은 그대로 둔다. 데이터는 읽기 전용이라 중복 표시에 부작용이 없다.

## 3. 구조 분석 — 되는 것 / 손봐야 하는 것

### ✅ 그대로 되는 것 (예상보다 많다)

**(a) 방향 표기** — `RouteItem.tsx:21`
```ts
const routeLabel = route.from ? `${route.from} → ${route.to}` : `${originName} → ${route.to}`
```
`from`이 있으면 `from → to`로 렌더된다. 도착 탭이 이미 이 경로를 쓴다.
→ **"완도 → 제주"를 그리기 위한 새 컴포넌트가 필요 없다.** 데이터에 from/to만 맞게 넣으면 된다.

**(b) 매칭 엔진** — `makeDepGroupKey` / `makeArrGroupKey`
routeGroup을 "출발항 1곳 → 제주"로 정의하면 기존 로직이 그대로 맞는다.
```
{ key:"wando", label:"완도", depPortKeywords:["완도"], destKeywords:["제주"] }
```
- dep 매칭: oport⊃"완도" && dest⊃"제주"  → 완도발 제주행 ✅
- arr 매칭: oport⊃"제주" && dest⊃"완도"  → 제주발 완도행 ✅

**(c) 부속 페이지** — `/jeju/ads`, `/jeju/qr`, sitemap은 `REGIONS` 기반이라 자동 생성된다.

**(d) 탭 UI** — `RegionNav`는 `repeat(N, 1fr)` 균등분할이고 주석에 "≤6개까지 안전". 5개는 범위 내.

### ⚠️ 손봐야 하는 것

| # | 항목 | 내용 |
|---|---|---|
| 1 | **from/to 방향** | `RegionConfig.inbound?: boolean` 추가. true면 `getRoutesForRegion`이 `from: cfg.label, to: config.name`으로, `getArrivalsForRegion`이 `from: config.name, to: cfg.label`로 채운다. 지금은 `to: cfg.label`만 채운다 |
| 2 | **탭 문구** | "제주 출발 / 제주 도착"이 아니라 **"제주 가는 배 / 제주 나오는 배"** 가 자연스럽다. `RegionRouteTabs`의 탭 라벨을 config에서 주입받게 |
| 3 | **요약 바 라벨** | `statusSummary`의 `labelOf`가 "제주 → 완도"로 나올 것. inbound일 때 뒤집기 |
| 4 | **mainTerminal 개념 부적합** | 제주는 출발항이 5곳. region의 `mainTerminal`은 "제주항 연안여객터미널"로 두고, 각 routeGroup에 `depTerminal`(완도여객선터미널·목포항국제여객터미널·진도항·녹동신항·삼천포항)을 넣는다 |
| 5 | **날씨·조석 기준** | 아래 별도 항목 |

## 4. 가장 고민이 필요한 지점 — 날씨를 어디 기준으로 보여줄 것인가

결항을 결정하는 것은 **항로 전 구간의 기상**이지 도착지 날씨가 아니다.
제주 페이지에 제주 날씨만 띄우면 "제주는 맑은데 배는 결항"이 흔히 생겨 **오해를 유발**한다.
이 앱의 신뢰가 걸린 부분이라 대충 넘기면 안 된다.

선택지:

- **A. 제주 기준 날씨 + 안내 문구** — 구현 최소. "출발지 기상에 따라 결항될 수 있습니다" 문구 필수.
- **B. 날씨 카드 생략, 운항 현황만** — 오해 원천 차단. 대신 페이지가 허전하다.
- **C. 노선 카드마다 출발지 파고 표시** — 가장 정확하지만 격자 5개 추가 호출 → 쿼터 부담.

> 현재 판단: **A로 시작하고, 문구를 명확히.** C는 쿼터를 보고 나중에.
> 제주 KHOA 관측소 코드는 미확인 — 작업 시 `obsvtrNm`으로 검증할 것.

## 4-1. 결정 — 도착 탭은 **유지한다** (검토 완료)

검토안: "제주 탭은 출발(육지→제주)만 다루고, 제주발(제주→육지)은 상세 페이지 안에 넣는다."
→ **채택하지 않는다.** 근거 셋:

1. **비용이 반대로 든다.** `getMtisDay`가 `cache(...)`라 도착 데이터는 이미 받아온 것을
   재사용한다 — API 호출 0건 추가, 즉 지금은 공짜다. 반면 상세로 옮기려면
   `RouteDetail`이 `route` 하나만 받는 구조라 `페이지 → RouteTabs → RouteItem → RouteDetail`
   전 경로에 왕복 데이터를 새로 흘려보내고 출발편↔귀항편 짝짓기 로직도 만들어야 한다.
   **줄이는 게 아니라 늘리는 작업이다.**
2. **핵심 원칙 #1과 충돌.** "탭·버튼으로 숨기지 않는다". 탭은 기존 패턴이지만
   상세 페이지 안은 카드를 눌러야 나오는 한 단계 더 깊은 곳이다.
3. **수요가 대칭이다.** 제주행 11편 / 제주발 10편으로 거의 같다. 렌터카·화물을 싣는
   이동은 비행기가 아니라 배라서 제주에서 나오는 수요가 작지 않다.
   또 나머지 4개 지역이 모두 출발/도착 탭을 가지고 있어 제주만 없으면 일관성이 깨진다.

**확정 사항**: 출발/도착 탭 구조를 그대로 쓰고 **탭 문구만 교체**한다.

```
[ 제주 가는 배 ]   [ 제주 나오는 배 ]
```

("제주 출발 / 제주 도착"은 어느 쪽이 육지행인지 헷갈린다.)

## 6. 작업 순서 (예상)

1. `RegionConfig.inbound` + `regionFerry`의 from/to 분기 (엔진, 소규모)

## 7. 부수 효과 — 기대되는 것

- 제주는 검색 수요가 압도적이라 **유입 증가폭이 가장 클 페이지**가 될 가능성이 높다.
- 광고 관점: 제주 탭이 생기면 광고 구좌가 하나 늘고, 여행사에는 "제주 포함 5개 지역"으로 제안할 수 있다.
  (현재 홍익여행사 제안은 4개 지역 기준 — 제주 추가 시 단가 재산정 여지)

## 8. 보류 — 별도 과제로 검토할 것

### 상세 페이지에 "돌아오는 편" 표시 (전 노선 공통)

제주 탭 검토 중 나온 아이디어. **제주만의 문제가 아니라 전 노선에 유용하므로 분리한다.**

- 완도→청산도 상세에서 청산도→완도 시간표를 함께 보여주면, 당일치기 이용자가 가장 궁금해하는
  "몇 시 배로 나와야 하나"가 한 화면에서 해결된다. 인천→백령도, 목포→홍도도 동일.
- 필요한 작업: `RouteDetail`에 귀항편 데이터 전달 경로 신설 + 출발편↔귀항편 짝짓기.
  순환항로(모도·외달도·독도 등)는 귀항편이 별도로 존재하지 않으므로 예외 처리 필요.
- **제주 탭 작업에 끼워 넣지 말 것.** 두 작업이 엉키면 둘 다 늦어진다.

> 상태: 아이디어만. 우선순위·구현 방식 미정.

## 9. 다음 단계 — 울릉도 (제주 완료 **후** 착수)

### 9-1. 데이터 실측 (MTIS 7일치)

울릉도행 출발항은 **4곳**. 강원권이 포항권보다 편수가 많다.

| 출발항 | 일평균 | 도착 | 선박 | 현재 커버 |
|---|---|---|---|---|
| **묵호**(동해) | 1.0편 | 울릉(도동) | 씨스타1호 | ❌ |
| **강릉** | 0.9편 | 울릉(저동) | 씨스타5호 | ❌ |
| 영일만신항 | 0.7편 | 울릉(사동) | 뉴씨다오펄호 | ✅ |
| 포항 | 0.7편 | 울릉(사동·도동) | 엘도라도익스프레스호 | ✅ |

신규는 묵호·강릉 = 일평균 1.9편. (제주 신규분 3.2편보다 작다 → 우선순위가 뒤인 이유)

### 9-2. 핵심 판단 — 포항 탭을 **울릉도 탭으로 흡수**한다

포항 페이지의 노선은 **전부 울릉도행**이다(포항→도동, 영일만→사동, 울릉→독도).
다른 목적지가 없다. 즉 **울릉도 탭은 포항 탭을 완전히 포함**하며, 강릉·묵호만 더해진다.

```
[완도] [울릉도] [목포] [인천] [제주]     ← 탭 5개 유지 (포항 자리를 울릉도가 대체)
```

- 탭을 6개로 늘리지 않아도 된다. 375px에서 6개는 각 55px로 빡빡하다.
- **출발지 탭(완도·목포·인천)과 목적지 탭(제주·울릉도)이 한 줄에 섞이는 문제**도 완화된다.
- 사용자 관점에서도 낫다. 포항 페이지 방문자는 포항이 아니라 **울릉도**가 궁금한 사람이고,
  검색량도 "포항 배편"보다 "울릉도 배편"이 크다.

**울릉도 탭 구성(안)**
```
울릉도 가는 배 / 울릉도 나오는 배
  포항       → 울릉도(도동)
  영일만신항   → 울릉도(사동)
  강릉       → 울릉도(저동)   ← 신규
  묵호       → 울릉도(도동)   ← 신규
  ─── 광고 ───
  [포항역 KTX 섹션]        ← 기존 유지
  [울릉도 → 독도 섹션]      ← 기존 유지 (islandHops)
```

### 9-3. 주의할 점

| # | 항목 |
|---|---|
| 1 | **`/pohang` URL 리다이렉트 필수.** QR·블로그·검색엔진에 이미 퍼져 있다. `/ulleung`으로 301 |
| 2 | KTX 섹션은 포항역 기준이라 그대로 유지. 다만 강릉·묵호 이용자에게는 무의미하니 "포항 출발 시" 맥락을 붙일 것 |
| 3 | 날씨·조석 기준이 애매해진다. 출발항이 포항(동해남부)·강릉·묵호(동해중부)로 흩어진다. 제주 4절과 같은 문제 |
| 4 | 독도 islandHops(`depKeyword:"울릉"`)는 그대로 동작. 손댈 필요 없음 |
| 5 | 확인 필요 값: 강릉항·묵호항 정식 터미널명, 씨스타1호/5호 선사·예매 링크, 지역 slug(`ulleung`?) |

### 9-4. 순서를 지킬 것

제주를 먼저 끝내고 착수한다. 이유:

1. 제주가 실익이 크다(신규 3.2편 vs 1.9편).
2. 제주로 `inbound` 엔진과 목적지 탭 구조를 **검증한 뒤** 울릉을 얹으면 위험이 낮다.
3. 함께 하면 "엔진 신규 + 탭 구조 개편 + 포항 탭 흡수 + URL 리다이렉트"가 한꺼번에 엉킨다.
   깨졌을 때 원인을 찾기 어렵다.

> 울릉은 **포항 탭을 없애는 결정**이 걸려 있어 제주보다 무거운 작업이다.
